# Spike report: OD-01 Unattended stock PiG sessions

## Effort budget

- **Budget:** 3 story points (decision-owned spike agreed in the architecture interview for OD-01).
- **Spent:** 2 story points. All four probes (P1 to P4) ran; nothing was cut. Model turns used: 14 of the 20 aimed for, all on `opencode-go/beam-free` with one-line prompts.

## Question

- **Owner:** `OD-01`
- **Decision this spike must produce:** Which hosting form keeps an unattended stock PiG 0.7.0 session alive and reachable in two situations: (1) a headless root whose turn has ended while extension-owned background work continues, and (2) a background detached session started by an extension in another PiG process that must outlive that process, stay alive while idle, and accept new input later. The options are "Print mode held open by the extension", "RPC mode with an input channel held by a helper", and "Pane hosts only".
- **Enough evidence:** For (1), a stock `pig -p` run stays alive after its first turn, later runs another turn in the same session file, and exits normally. For (2), a process started from an extension survives both a normal exit and a SIGKILL of its launcher, stays alive while idle, and runs a further turn from new input.

## Context and objective

- **Triggering upstream file or section:** `.constitution/reports/open-decisions.yaml` entry `OD-01` (blocks CAP-039, CAP-047, CAP-062) and `.constitution/reports/2026-11-25-interview-architecture.md`, item "Unattended hosting is closed by a spike".
- **Target:** The lifecycle boundary of stock PiG print mode (`coding/cli/print_mode.go`), the `agent_before_settle` boundary (`coding/session_boundaries.go`), RPC mode's stdin-EOF shutdown (`coding/cli/rpc_mode.go`), and the extension host's process-group teardown (`coding/extension/host/subprocess/process_tree_unix.go`).
- **Archetype / surface:** A Go extension for unmodified PiG releases on Linux and macOS (CAP-039), covering the headless root keep-alive (CAP-062) and the background form of a detached session (CAP-047).

## Codebase baseline

- **State today:** The repository has no implementation of either situation. Source reading of stock PiG 0.7.0 found the following. Print mode sends its prompts, waits for `FlushEvents`, writes the last assistant message, then closes the runtime (`session_shutdown`) and exits (`print_mode.go` `runPrintModeIn`). Nothing in print mode waits for later input. `runBeforeSettleBoundary` dispatches `agent_before_settle` and continues the run when a handler returns `continue: true` with runnable context, or when messages are queued (`session_boundaries.go`). Boundary handlers have no completion deadline; the host heartbeat proves only that the extension transport is alive, not handler progress (docs `extensions.md`, "Connection and liveness model"). The extension host starts each extension process with `Setpgid` and, at teardown, sends SIGKILL to the whole process group (`process_tree_unix.go` lines 20 and 44). RPC mode exits when standard input ends (`rpc_mode.go` `runRPCMode`). In RPC mode `ctx.hasUI` is `true`, and dialog methods without a `timeout` wait for a client's `extension_ui_response` (docs `rpc-extension-ui.md`). In print mode `ctx.hasUI` is `false`.
- **Discovered constraints:** (a) Anything an extension spawns without leaving the extension's process group dies with it when the host tears down. (b) Print mode offers no window after `agent_settled` in which a background goroutine can act. (c) Pi docs state that an aborted run skips `agent_before_settle` and goes straight to `agent_settled`, so an abort ends a held print run (source and docs only, not measured). (d) The extension directory name must equal the name passed to `sdk.New`, otherwise loading fails with `register:name_mismatch`.

- **Public interface and command:** One scratch Go extension, `$T/spk` (scaffolded with `pig extension init`), configured through environment variables. Its `agent_before_settle` handler holds the run for a fixed number of poll cycles. In each cycle it calls `ctx.Sleep` and checks for input, from a marker file `marker-<n>` or a line on a Unix socket it listens on. When input arrives, it either returns a continuation or calls `SendUserMessage(msg, "followUp")`:

  ```go
  e.OnEvent("agent_before_settle", func(ctx sdk.Context, data map[string]any) (any, error) {
      entries, _ := data["entries"].([]any)
      for poll := 1; poll <= maxPolls; poll++ {
          _ = ctx.Sleep(pollEvery)
          msg := nextInput() // marker file or socket line
          if msg == "" { continue }
          if msg == "quit" { return nil, nil }
          entries = append(entries, map[string]any{"type": "custom_message", "customType": "spk-input", "content": msg, "display": true})
          return map[string]any{"entries": entries, "continue": true}, nil
      }
      return nil, nil
  })
  ```

  Its `/launch` command starts process 2 from inside process 1. Print mode runs an extension command in place of the prompt, so process 1 uses no model turn:

  ```go
  cmd := exec.Command("/bin/sh", "-c", os.Getenv("SPK_CHILD_CMD"))
  cmd.Stdin, cmd.Stdout, cmd.Stderr = devnull, devnull, devnull
  cmd.SysProcAttr = &syscall.SysProcAttr{Setsid: true} // SPK_SETSID=0 omits this
  _ = cmd.Start(); _ = cmd.Process.Release()
  ```

## Options and trade-offs

- **Print mode held open by the extension.** Situation (1): works. It is the only measured way to keep a `pig -p` run alive after its turn: holds of up to 400 poll cycles, turns 2 and 3 in the same session, through both a returned continuation and `SendUserMessage` follow-up, and exit status 0 on release. Situation (2): works when the launcher starts the process with Setsid. It survived 2 of 2 launcher exits (normal and SIGKILL) and accepted a socket line after 9 and 61 idle poll cycles. No helper process is needed, because the extension owns both the keep-alive and the input path. `ctx.hasUI` is `false`, so no dialog can block on a missing client. Costs: the session never reaches `agent_settled` while held, so it reads busy rather than idle to anything that waits for idle. Text stdout carries only the last answer; intermediate answers are only in the session file (or the event stream with `--mode json`). Nothing can run after `agent_settled` (P1b). The session lives only as long as the hold handler and its extension process. Per docs, an abort skips the hold and ends the run.
- **RPC mode with an input channel held by a helper.** Situation (1): not applicable to a `pig -p` headless root. Using it would mean the operator runs the root in RPC mode behind a client, which is not the headless form CAP-039 names. Situation (2): works when started with Setsid. It survived 2 of 2 launcher exits, answered `get_state` with no model cost, ran further prompts after idling, and exited cleanly (status 0) when the helper released the FIFO. It is truly idle between turns and streams every event on stdout. Costs: a helper process must own stdin and be supervised, and when the helper dies the session ends. `ctx.hasUI` is `true`, so per docs any extension dialog without a `timeout` waits forever for a client that does not exist. Custom views do nothing in RPC mode. Pig Litter would also carry another hosting mechanism besides the one for situation (1).
- **Pane hosts only.** Works as the baseline for the pane form of a detached session: two turns after the launcher exited, clean `/quit`. It does not answer situation (1) at all and requires a pane host. The launcher must also keep `tmux` alive until its server daemonizes (setsid or a short block). The evidence above rules out the premise that only a pane host can own a long-lived detached session.

## Recommendation

- **Chosen option:** Print mode held open by the extension. For situation (1), the headless root, it is the only option that applies and it works. For situation (2), the background detached session, it is also chosen, launched with Setsid and with the extension's own socket as the input path. RPC mode with an input channel held by a helper was measured working for (2) and is the fallback.
- **Why it fits:** One mechanism serves CAP-062 and the background form of CAP-047 on stock PiG (CAP-039), with no helper process to build or supervise. The Pig Litter extension must already own an input path for peer messages, and that same path drives the continuation. `hasUI=false` avoids the dialog-blocking failure mode of a client-less RPC session. The pane form of CAP-047 still uses a pane host where one is available, which P4 confirmed.
- **Rejected options:** RPC mode with an input channel held by a helper: it works for (2) but cannot serve (1), adds a supervised helper whose death ends the session, and risks dialogs that block without a client. Pane hosts only: it cannot serve a headless root or a terminal-less launcher, and the probes show it is not the only working host.

## Downstream impact

- **ADRs to write or update:** An ADR for unattended hosting: a held `agent_before_settle` hook for a headless root, and a Setsid-launched held print session for background detached sessions. The path is decided at Stage 3.
- **Tickets unblocked:** none
- **Work still held:** none beyond the spec edits below; CAP-039, CAP-047, and CAP-062 can proceed on the chosen option.
- **Register entry closed:** OD-01, chosen option "Print mode held open by the extension".
- **Tickets to add or split:** When the plan is written, add work for (a) the before-settle hold loop that re-holds at every settle while descendants or peers may still send input, (b) the Setsid launch with detached stdio, and (c) the extension-owned input listener for background detached sessions.
- **Spec edits required:** Stage 2 architecture must carry these stated limitations. A detached or background launch must start a new session (Setsid) with stdio detached from the launcher, because the host SIGKILLs the extension's process group (control survived 0 of 1). Without that, even `tmux new-session -d` can be killed before its server starts. A held print session never reports idle or `agent_settled` while held, and nothing can run after `agent_settled` in print mode. The session ends if the hold handler or its extension process ends, or (per docs, unmeasured) if a run is aborted. Text stdout carries only the final answer. The interview accepted that "a headless root that coordinates detached sessions exits after its turn and misses their messages". This spike shows a held root can stay alive and receive them, so Stage 2 may revisit that acceptance.
